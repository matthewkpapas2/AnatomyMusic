## 1. Why a session stopped at 10 minutes
`MAX_SEC = 600` in `web/js/app.js`. The engine sizes its per-frame history for it and stops when it's full; the page
keeps the whole recording for replay; the Shape compares every half second with every earlier one. Computed from the
array sizes at 48 kHz (not measured in a browser):

| Session | Recording + per-frame history | Shape rows + its image | Total |
|---|---|---|---|
| 10 minutes | 75 MB | 12 MB | about 90 MB |
| 30 minutes | 225 MB | 105 MB | about 330 MB |
| 1 hour | 450 MB | 415 MB | about 865 MB |
| 3 hours | 1.35 GB | 3.7 GB | about 5 GB |

So "no limit" on one session isn't possible; the limit has to move off the session.

## 2. How long a fresh engine needs (Node, Demo 1 at 48 kHz, live settings)
| Started at | Beat locked after | Key shown after | First section after | Engine CPU |
|---|---|---|---|---|
| 0:00 of the song | 8.5 s | 5.0 s | 17.5 s | 39–45 ms per second of audio |
| 0:20 | 4.4 s | 5.0 s | 29.0 s | 40–42 ms |

Making a new engine takes 2–10 ms. So a second engine can warm up beside the first for about 4% of one core, and 60 s
is enough for the beat, the key and a first section. That's where `WARM_MIN = 60` comes from; `WARM_LEAD = 150` leaves
a 90 s window to wait for a section change. Both are judgment calls from one synthetic song (tech debt #49).

## 3. What was built
Microphone and tab sessions hand over to a warmed-up engine instead of stopping (`docs/01-architecture.md`, "listening
sessions"). The picture is kept across the handoff; Analysis and replay cover the current session only. Also a screen
wake lock while listening.

## 4. Measured: the real microphone path, headless Chromium
The fake capture device loops a WAV of Demo 1 (122 BPM) and Demo 2 (126 BPM). Headless draws Visuals at about 2.6
frames a second (software WebGL).

| | Real constants (600 / 150 / 60 s) | `--fast` (100 / 50 / 20 s) |
|---|---|---|
| Listened | 20:37 (1232.6 s in 1233.4 s of wall clock) | 5:34 (334.2 s in 334.7 s) |
| Handoffs | 2, at 515 s and 519 s into their sessions | 6, at 71–83 s |
| What triggered them | a section change (neither waited for the 600 s cap) | a section change (none waited for 100 s) |
| Beat across each handoff | locked; 126.0 → 126.0 and 122.8 → 122.8 BPM | locked; same tempo on all 6 |
| Particles, frame before → after | 103 → 104, 122 → 107 | 116 → 117, 97 → 96, 167 → 139, 175 → 153, 494 → 468, 155 → 147 |
| Listening clock across each handoff | advanced 0.37 s and 0.51 s over 0.42 s and 0.44 s between frames | 5 of 6 within the 0.5 s tolerance of the first version of the check; the 6th advanced 0.76 s between two slow frames |
| Samples with onset hits after a handoff | 125 of 137 | 46 of 51 |
| Page errors | 0 | 0 |
| JS heap as Chrome reports it | by session: lowest 27 / 37 / 38 MB, mean 64 / 72 / 65 MB; highest 153 and 164 MB just before each handoff, while two sessions are in memory | peak 36 MB after handoff 1, 35 MB after handoff 6 |
| Status after Stop | "Session finished after 20:37 of listening. Analysis and replay cover the last 5:37. …" | "…after 5:38 of listening… the last 0:38. …" |

The `--fast` run above is the last one made before the clock check was changed to compare against the time between
the two frames; the real-constants run used the final test. `--fast` wasn't repeated with the final check.

**Memory:** the heap falls back after each handoff (153 → 38 MB within 10 s of the first; 164 → 38 MB within 25 s of
the second), so the old session is released. Three sessions are too few to rule out a slow leak; that needs a
longer run (section 6).

**Tempo between handoffs:** 14 of the 236 samples in the long run were unlocked or off the two demo tempos (61.5,
121.3, 123.2, 139.4, 139.6 BPM, or no lock). 5 of them came before the first handoff, so this is the engine re-locking
where the looped file jumps from one song to the other, not the handoff.

**Controls** (`--fast`, one handoff each feature switched off): with the Visuals handoff off, particles went 96 → 2
and 135 → 1 (the picture resets); with the `lastSpawnF` line removed, only 2 of 13 samples after a handoff saw onset
hits.

## 5. Two existing bugs found on the way (both in v7)
1. **Clicking the microphone before the built-in demo finished analyzing** fed the demo song into the microphone
   session and, when the demo finished, stopped that session and stored it as the demo. Seen in the first test run:
   the session clock ran at twice the wall clock, the tempo read 64–129 BPM, and listening stopped at about 76 s. On a
   fast machine the window is short, but it's the first thing someone setting up for a set would click. Fixed: the demo
   analysis stops if another session starts.
2. **After any session, the next one threw no onset shards** until it had run longer than the previous one, and
   seeking backward in a replay did the same: `S.lastSpawnF` (the frame of the last shard) was never reset. Fixed
   where the frame count is read. Measured only for the handoff case (the control above); the new-session and replay
   cases are the same line, read but not separately measured.

## 6. Not measured
- **How it looks.** The test counts particles and reads the beat lock. Whether a section color changing at a handoff
  is noticeable needs eyes on a real screen. The new engine's section letters start again from A.
- **A real set.** No run longer than 21 minutes, no real microphone or mixer feed, no real GPU. Process memory wasn't
  read, only Chrome's JS heap figure.
- **The wake lock on a real display.** Headless Chromium refuses the lock by default ("permission request denied"), so
  in both test runs above it was never held and only the "not available" path ran. Checked separately: with the
  permission granted to the page, the lock is held while listening, released on Stop and taken again on the next
  start, with 0 page errors; and Chromium calls both `http://127.0.0.1` and a page opened from a file a secure
  context, so the API is there either way. Whether a real Mac's display then stays awake wasn't tested.
- **The pair harness** (unchanged code paths, see section 0).
